**Y-Offset on some of the assets**

From testing Ray discovered some bugs remining in the system for which the asset will have 
y-offset issue when performing the certain command (POS/ROTAT). Current assets with this issue 
including `piano.gltf` and `hockney_table.gltf`.

From discovery in `metadata.json` We suspect that the center of the `gltf` item is not in the miidle 
point instead a roughtly 0.3 y-offset (probably `{x: 0, y: -.3, z: 0}`, while center supposed to 
be `{x: 0, y: 0, z: 0}`).

To reproduce the issue, 

- first user say: add a piano, and place it in the middle of the room, the system responds with correct processing.

- then when user say: move this piano to the back wall of the room, then the system malfunctioning with a y-offset -.3 applied 
to the item when moving it.

**System Conversational Memory**

A feature need to refine is the conversational memory. For which the conversational memory module need to be able to remember the 
context between user and the system. To keep it compact while still demonstrating the feature. We ensure that the language agent have the access to 
a memory pole which stores user's latest 5 commands and keetp rolling.

**The conversational memory should be accessed at the Language Agent stage!** Ken's framing is that the system should decompose commands **the way a 
human listener would**. A human listener resolves ambiguous references using conversational context before deciding what action to take — not after.

Consider: 

- Turn 1: "add a desk near the back wall"

- Turn 2: "now rotate it 90 degrees"

"it" is a deictic reference to the desk from Turn 1. This needs to be resolved at **language parsing time** — the Language Agent needs to know 
"it = desk_01" before it can classify the command as `POS/ROTATE` and identify the involved object. If the memory is only accessed at SceneAgent, 
the Language Agent outputs `involved_objects: ["it"]` which breaks the whole downstream pipeline.

Design:

Voice input
    ↓
Language Agent reads rolling 5-command memory

One thing to note, this only happens in `POS/ROTATE` branch, since in `ADD/DELETE` branch it already have clear reference which is the newly 
added item. For example: "add a table, and place it in the middle of the room", we do not need to resolve thsi with conversational memory.

## Embodiment Tracking Design

**A design discussion on conversational memory, gaze tracking, and how humans actually communicate in space**

### The Problem With "It"

Natural language is full of references that only make sense in context. When a user says "rotate it 90 degrees", the word "it" carries no 
geometric information — it's entirely dependent on what came before. When a user says "move it to the wall" while physically turning their 
head toward a specific table, "it" means something completely different.

This distinction turned out to be the crux of a design question: **when should the system use conversational memory, and when should it 
use gaze tracking?**

### 3 Scenarios, Different LEVELS of Resolvers

Consider a room with six tables. The user has been adding furniture through voice commands, most recently adding `table_06`. Then:

- **Scenario A:** User says "rotate it 90 degrees" — Here "it" almost certainly refers to the most 
recently touched object. Conversational memory is the right resolver — look back at the last turn, find table_06, apply the rotation.

- **Scenario B:** User walks across the room, turns their controller toward a place, and says "move this table there". the system should be able to 
track the user's position, and find the closest euler position `sqrt(x^2 + z^2)` item named after table and tracks the user's controller's pointing position. 

- **Scenario C:** User looks at a cup, and say, "place the cup on that table", the system should be tracking the cup closest to user's position and for "that table", 
system tracks user's pointer and calculates the find the item named table closest to pointer using euler position `sqrt(x^2 + z^2)`.
